Flutter 技术架构选型

已有结论：Flutter + sqflite 本地存储 + JSON 导入/导出 + 全免费

方案对比：状态管理 + 架构模式

A · Riverpod + 分层架构（推荐）

Pros

  • 编译期安全，无 BuildContext 依赖
  • Provider 替代品，社区活跃
  • 适合中等规模、状态复杂的 App
  • 测试友好（override provider）

Cons

  • 学习曲线略高于 Provider
  • 概念较多（Notifier/AsyncNotifier/...）

数据层 (sqflite + API) → 领域层 (SRS算法) → 表现层 (Widgets)

B · BLoC + 事件驱动

Pros

  • 事件/状态分离清晰，日志天然可追踪
  • 大团队标准实践（Google 推荐）
  • 可测试性极高

Cons

  • 模板代码多（Event + State + Bloc 三件套）
  • 单一开发者维护成本偏高
  • 简单操作也要写 Event，变重

C · Provider + MVVM

Pros

  • 最简单、Flutter 官方入门推荐
  • 上手成本最低
  • 对这个规模的 App 够用

Cons

  • 依赖 BuildContext，导航/弹窗场景尴尬
  • 复杂状态组合能力弱
  • 后期重构成本高

我的推荐：Riverpod

WordSnap 的状态复杂度不低：SRS 复习状态机、剪贴板监听、多录入模式、筛选排序。Provider 在导航/弹窗场景会卡壳；BLoC 模板过多拖慢单人开发速度。Riverpod 是合理中间态——足够安全，不过度。
